### Setup and Teardown

No setup or teardown is needed. Selenide opens the browser on the first call to `open()`, and closes it
automatically when the tests finish.

### Why Not Just `shouldHave`?

Selenide already retries on its own: a check like `shouldHave(text(...))` keeps checking the element until the
condition is met or the timeout (4 seconds by default) runs out. But it only waits. It doesn't repeat the actions
that produced the page, and here the message changes only when the page is loaded again.

So instead of writing our own retry loop, we use Awaitility, a small library for exactly this: it repeats a
condition until it returns `true` or a timeout runs out.

### The Test

In the test, we first declare the notification element with `$("#flash")`. Selenide finds elements lazily, so this
works even before the page is loaded: the element is looked up again every time we use it.

Then, in lines 17 to 20, we ask Awaitility to repeat our actions for up to 30 seconds: load the page, and check
whether the notification has the successful message. `flash.has(text(...))` checks the element right away and
returns `true` or `false`, without waiting and without failing the test.

`pollInSameThread()` matters here: by default, Awaitility runs the condition in a separate thread, but Selenide keeps
one browser per thread, so we run it in the test's thread to keep using the same browser.

Unlike the other languages, we limit the retries by time rather than by number of attempts. Loading the page takes
about a second, so 30 seconds allows plenty of attempts. If the successful message still hasn't shown up by then,
Awaitility throws a `ConditionTimeoutException` and the test fails.
